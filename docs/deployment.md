# Deployment guide

This guide deploys the React frontend as a static site and the FastAPI service
as a separate web service. It uses Render for both services and a managed
PostgreSQL database. Choose the same settings if you deploy on another host.

## 1. Prepare the production network

Choose an EVM network and RPC provider. Do not use Hardhat's ephemeral local
network for a public deployment. Deploy `ExperimentRegistry` using a dedicated,
funded service wallet. Use a wallet with only the permissions and funds needed
for registry writes; never use a personal wallet or commit its key.

From the repository root, install and compile the contract:

```powershell
Set-Location blockchain
npm ci
npm run compile
```

Set `BLOCKCHAIN_RPC_URL`, `BLOCKCHAIN_CHAIN_ID`, and `BLOCKCHAIN_PRIVATE_KEY` in
the shell environment or an ignored local `.env` file in the repository root.
Then deploy:

```powershell
npm run deploy:configured
```

Save the printed contract address as `BLOCKCHAIN_CONTRACT_ADDRESS`. Use the
same chain ID and RPC URL for the API service. Keep the private key only in the
API host's encrypted secret settings. The contract address is public; the key
is not.

## 2. Deploy the API and database

Create a managed PostgreSQL database, then create a Python web service connected
to this GitHub repository. Use `backend` as its root directory and configure:

| Setting | Value |
|---|---|
| Build command | `pip install ".[postgres]"` |
| Start command | `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT` |
| Python | 3.11 or newer |

Set these environment variables in the API service:

| Variable | Value |
|---|---|
| `APP_ENV` | `production` |
| `JWT_SECRET` | A unique random secret generated by the host |
| `DATABASE_URL` | The managed PostgreSQL connection string |
| `ARTIFACT_STORAGE_DIR` | `/opt/render/project/src/storage` |
| `BOOTSTRAP_ADMIN_EMAIL` | Email address for the first administrator |
| `BOOTSTRAP_ADMIN_TOKEN` | A long one-time setup token; store it as a secret |
| `CORS_ORIGINS` | The exact HTTPS origin of the frontend, added after step 3 |
| `BLOCKCHAIN_RPC_URL` | RPC URL for the selected EVM network |
| `BLOCKCHAIN_CHAIN_ID` | Numeric chain ID for that network |
| `BLOCKCHAIN_CONTRACT_ADDRESS` | Address printed by the contract deployment |
| `BLOCKCHAIN_PRIVATE_KEY` | Dedicated service signer key, stored as a secret |

The API accepts common `postgres://` and `postgresql://` connection strings and
uses the installed `psycopg` driver. Keep TLS enabled for the database
connection. The start command applies the checked-in Alembic migrations before
starting the service.

Attach a persistent disk at `/opt/render/project/src/storage` for generated
artifacts. Confirm the selected host and service plan support persistent disks;
otherwise, artifacts will be lost when the service is replaced. This app writes
artifacts to local filesystem paths, so one API instance must use that disk.

## 3. Deploy the frontend

Create a static-site service from the same repository with `frontend` as its
root directory:

| Setting | Value |
|---|---|
| Build command | `npm ci && npm run build` |
| Publish directory | `dist` |

Set `VITE_API_BASE_URL` to the public HTTPS URL of the API, with no trailing
slash, for example `https://your-api.example.com`. This value is embedded in
the frontend build and is public; never put passwords, signing keys, or other
secrets in a `VITE_` variable.

After the static site has a stable URL, set `CORS_ORIGINS` on the API to that
exact origin (scheme and host, with no path), then redeploy both services.

## 4. Create the first administrator and smoke-check the app

Before creating any account, register once with the configured bootstrap email
and token. The matching account receives the administrator role only if no
administrator exists yet. Store the token outside the application and rotate
or remove it after the first administrator is created.

Check API health at `https://your-api.example.com/api/health`. Then sign in and
confirm that you can:

1. Create an experiment and choose model parameters, a version, and source
   repository/commit metadata.
2. Review its metrics and download an evidence artifact and JSON report.
3. Verify file hashes, anchor the manifest, and inspect the transaction.
4. Run a reproduction with a chosen metric tolerance and review the comparison.

## Operational constraints

- Use HTTPS for the frontend, API, database, and RPC provider.
- Keep the API signing key, database URL, JWT secret, and administrator token
  in the host's secret manager. The browser receives only `VITE_API_BASE_URL`.
- This release records training and reproduction work as FastAPI background
  tasks. A process restart can interrupt active work. Keep a single API
  instance and avoid deploying during active runs. For sustained production
  workloads, move jobs to a durable worker queue before scaling horizontally.
- Artifacts use a mounted local disk. Back it up and restrict access. For
  multi-instance deployments, move artifact storage to private object storage
  and update the storage adapter first.
- Configure database backups and monitor API logs, disk capacity, job failures,
  RPC availability, and transaction confirmations.
- The reproducibility score is an explainable project heuristic. It is not a
  scientific certification or a substitute for methodological review.
